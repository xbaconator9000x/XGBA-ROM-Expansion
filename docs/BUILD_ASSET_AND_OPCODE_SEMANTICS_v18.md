# Phase 1 — generated assets and indirect bytecode dispatch (v1.8)

**Source revisions:** FireRed `ce6406d8c2eaf46d543c8a2606de0c3cb1951982`. This document describes source-verified architecture, not all-file semantic signoff or working emulator patches.

## 1. Why thousands of graphics resource references are not tracked files

[FireRed Makefile lines 245–268](https://github.com/pret/pokefirered/blob/ce6406d8c2eaf46d543c8a2606de0c3cb1951982/Makefile#L245-L268) (blob `8b454dbd18eb0069fa5851d788697190890a5b37`) imports `graphics_file_rules.mk` and establishes generic graphics source-to-artifact rules:

| Build artifact | Default tracked input | Generator |
| --- | --- | --- |
| `%.1bpp` | `%.png` | `$(GFX)` |
| `%.4bpp` | `%.png` | `$(GFX)` |
| `%.8bpp` | `%.png` | `$(GFX)` |
| `%.gbapal` | `%.pal` **or** `%.png` | `$(GFX)` |
| `%.lz` or `%.rl` | matching uncompressed output | `$(GFX)` |

This is supplemented by [graphics_file_rules.mk](https://github.com/pret/pokefirered/blob/ce6406d8c2eaf46d543c8a2606de0c3cb1951982/graphics_file_rules.mk), blob `39b952cd45b6a34eb98318a76aa531fcafff134d`, including special concat/sprite/font recipes.

Concrete traced examples:
- `src/field_door.c` embeds generated `graphics/door_anims/sliding_double.4bpp`, derived from tracked `graphics/door_anims/sliding_double.png`.
- `src/mystery_gift_show_news.c` embeds generated `graphics/wonder_news/bg0.gbapal`; tracked `graphics/wonder_news/bg0.pal` (and a PNG) exist.
- `src/map_preview_screen.c` embeds generated `graphics/map_preview/viridian_forest/tiles.4bpp.lz`; tracked `graphics/map_preview/viridian_forest/tiles.png` exists, with a special [graphics_file_rules.mk:392–393](https://github.com/pret/pokefirered/blob/ce6406d8c2eaf46d543c8a2606de0c3cb1951982/graphics_file_rules.mk#L392-L393) tile-count conversion rule.
- Some assets are **composite**: [graphics_file_rules.mk:30–52](https://github.com/pret/pokefirered/blob/ce6406d8c2eaf46d543c8a2606de0c3cb1951982/graphics_file_rules.mk#L30-L52) concatenates multiple Castform graphics or palette fragments.

**Implication:** a source-reference analyzer that requires every `.4bpp` or `.gbapal` to be a tracked source file will report false missing dependencies. XGBA plugin/event/resource patching needs to follow **original PNG/PAL → converter invocation + transformation options → generated bytes → linker symbol/pointer consumer**. Existing 29,068-register file anchors remain correct but do not fully explain this generation chain. The new `tools/generated_asset_provenance.py` computes separate provenance candidates, storing rule SHA and consumer line numbers without pretending to execute Make.

## 2. Two disjoint opcode dispatch tables bypass direct static call graphs

[Field opcode registry](https://github.com/pret/pokefirered/blob/ce6406d8c2eaf46d543c8a2606de0c3cb1951982/data/script_cmd_table.inc), blob `c5d112d9ea66d258d5a372dda89b9ad96ed2b1e1`, declares `gScriptCmdTable::` followed by numbered `.4byte ScrCmd_*` handler pointers, then a distinct `gScriptCmdTableEnd::` sentinel. **Field bytecode opcodes run from `0x00` through `0xD4` (213 entries)**, with the end marker not an extra opcode.

[Field interpreter `src/script.c:115–137`](https://github.com/pret/pokefirered/blob/ce6406d8c2eaf46d543c8a2606de0c3cb1951982/src/script.c#L115-L137) (blob `d0433bdda062b138e53d1a1d3184b4566ad7d9dc`) looks up `ctx->cmdTable[cmdCode]`; the handler function definitions are in [`src/scrcmd.c`](https://github.com/pret/pokefirered/blob/ce6406d8c2eaf46d543c8a2606de0c3cb1951982/src/scrcmd.c), blob `97b695ee2f6fca80a3b78f52f6a444f696fe5814`.

[Battle opcode registry `src/battle_script_commands.c:312–564`](https://github.com/pret/pokefirered/blob/ce6406d8c2eaf46d543c8a2606de0c3cb1951982/src/battle_script_commands.c#L312-L564), blob `67f90a37044db87091b2174f78fe1e31ad2ef10d`, defines a C function-pointer array `gBattleScriptingCommandsTable`. **Battle opcodes run from `0x00` through `0xF7` (248 entries)**. At [`src/battle_util.c:3051`](https://github.com/pret/pokefirered/blob/ce6406d8c2eaf46d543c8a2606de0c3cb1951982/src/battle_util.c#L3051), blob `bb66a0144b6144a72e1d9b22321c541e22302f7e`, the interpreter calls `gBattleScriptingCommandsTable[*gBattlescriptCurrInstr]()` using the current bytecode opcode.

**Implication:** there are **461 distinct opcode slot positions, each with a handler role**, which are invisible to a regular direct-function-call graph. Tracking code changes in `scrcmd.c` without mapping its table into `script.c` is incomplete; likewise a change to battle commands must flow through both C table and `battle_util.c`. See `tools/dynamic_dispatch_semantics.py`, which verifies table continuity, pinned blob hashes, handler definitions and provides candidate operand width/role metadata per opcode.

**Still not proven:** compiled handler addresses, all argument formats, indirect secondary callbacks, version-dependent macros, whether all opcodes execute in a given storyline, safety of external handles in any individual command.

## 3. Completion boundary

These are source-backed facts, but **neither the generated graphic converter nor the opcode tables have been verified end-to-end in an emulator yet**. The source mapping gate remains `FAIL_INCOMPLETE` until every file has an adequately evidenced semantic disposition, including third-party libraries and generated artifacts.
