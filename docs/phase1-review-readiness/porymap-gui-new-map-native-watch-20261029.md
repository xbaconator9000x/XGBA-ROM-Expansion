## 2026-11-05 permission-probe diagnosis and fail-closed regression repair (CI pending)

Exact-head PR run [#41951099581](https://github.com/xbaconator9000x/XGBA-ROM-Expansion/actions/runs/41951099581), attempt 2, job `127105406708`, confirms the revised workflow executed the test with effective UID `1001`, built the pinned application, loaded the project, and reached the permission probe. It still failed at `FAIL permission_denial_probe`. The log's `Unrecognized commit history` is a warning; Porymap continued to monitor all 34 project files and select maps, so the warning is not the observed failure. Artifact `13396032203` (ZIP SHA-256 `af86bd3da059834f59c90b92cde462700a346059a04335f1e290eafe4f31f8b8`) contains the build log and native log, but not a core dump or debugger backtrace.

The old probe required Qt's specific `QFileDevice::PermissionsError` enum. It did not capture Qt's actual error code/string or independently prove the kernel denied creation, so the log does not establish a filesystem permission failure and cannot identify the precise Qt error classification. The test now checks the directory owner/mode and performs an `open(O_CREAT|O_EXCL)` negative that must fail with Linux `EACCES`, then separately requires Qt `QFile::open` to fail with a non-`NoError` result. A writable-create control runs before the chmod injection. Diagnostics record UID, owner/mode, errno, and Qt error/string, and the machine-readable transcript requires the EACCES and QFile-denial booleans. This preserves a strict actual permission-denial test without overfitting to a Qt enum.

The same log reports a segmentation fault immediately after `need()` printed the failed assertion. The test helper called `std::exit(3)` on assertion failure, which runs Qt static teardown; the available artifact has no backtrace, so the exact segfault stack is unproven and this is not attributed to pinned Porymap startup. The harness now uses `_Exit(3)` after flushing the failure message so a failed assertion is not obscured by teardown. This is a test-harness failure path, not a way to pass the permission test. A new exact-head native run must still verify permission denial and normal teardown; no new runtime claim is made here. Phase 1 remains FAIL_INCOMPLETE, 0/14,834 independent approvals.
